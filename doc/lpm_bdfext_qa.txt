**Core Design**:
- 6 DOF system: q = [x, y, z, u, v, w]^T (position + velocity)
- Decoupled equations: dx/dt = u (explicit), du/dt = A*u + f (implicit 3×3)
- solverOrder controls BOTH BDF and extrapolation (no separate nEXT)
- nDOFs_ = 6 for BDFEXT (vs 3 for AB/RK)

**Storage Strategy** (reuses existing infrastructure):
- o_y: 6 * fieldOffset (current position + velocity)
- o_ydot: solverOrder * 6 * fieldOffset → REUSED for A_hist (6 elements/level)
- Properties: f_hist (3×solverOrder) + q_hist (6×solverOrder) = 9×solverOrder/particle

**A Matrix Structure** (3×3 for velocity equation only):
- Anti-symmetric + diagonal: [a_11, a_22, a_33, a_12, a_13, a_23] (6 elements)
- Reconstruction: a_ij = -a_ji for off-diagonal
- Memory in o_ydot: [A^n(6) | A^{n-1}(6) | ... | A^{n-k+1}(6)]

**Computational Approach**:
- 3×3 implicit solve for velocity: M*u^{n+1} = b where M = (α_0/Δt)*I - A^{n+1}
- Explicit position update: x^{n+1} = f(u^{n+1}, x_history)
- ~50 FLOPs per particle (vs ~200 for full 6×6) → 4× speedup!

**Coefficients**:
- α: BDF discretization (α_0, α_1, ...) - variable dt support needed
- β: Extrapolation (follows laggedInterpFields/extCoeff pattern)

**Physics Evaluation**:
- Built-in models initially (user callback deferred)
- A and f computed from interpFields (velocity, vorticity, DuDt)
- Called once per timestep after interpolation

**Key Insights**:
- dx/dt = u is UNIVERSAL (holds for any physics model)
- Only velocity needs implicit treatment (position is kinematic)
- Position history saved for BDF accuracy, diagnostics, potential extrapolation
- Semi-implicit: velocity fully implicit, position uses new velocity

DESIGN EVOLUTION - How We Got Here
================================================================================

This section documents key design pivots and insights discovered during the
design process, for future reference and to explain the rationale.

**Initial Understanding → Correction**:
1. "A is a Jacobian" → "A is a coefficient matrix"
   - Early mistake: called A a "Jacobian matrix"
   - Reality: A is the coefficient matrix in du/dt = A*u + f
   - It's moved to LHS for implicit treatment, not for Newton iteration
   - See Q2 for correct explanation

**Major Design Decisions**:
1. solverOrder for both BDF and extrapolation (Q1)
   - Could have split: solverOrder for BDF, nEXT for extrapolation
   - Decision: unify under solverOrder for simplicity
   - Rationale: BDF-k with k-th order extrapolation is well-matched
   
2. 6 DOFs instead of 3 (Q2)
   - AB/RK only track position (3 DOFs), compute velocity via dx/dt
   - BDFEXT tracks position + velocity (6 DOFs)
   - Rationale: velocity needed explicitly for complex force evaluation
   - Benefit: enables richer particle dynamics models

3. Decoupled 3×3 solve instead of full 6×6 (Q3)
   - Initial plan: solve full 6×6 implicit system
   - Insight: dx/dt = u is UNIVERSAL, doesn't need implicit treatment
   - Optimization: only solve 3×3 for velocity, position is explicit
   - Impact: 4× computational speedup (~50 vs ~200 FLOPs)

4. Storage in o_ydot + properties instead of new arrays (Q17)
   - Could have: allocated new deviceMemory for A_hist, f_hist, q_hist
   - Decision: reuse o_ydot for A_hist, use properties for f_hist/q_hist
   - Rationale: no migration changes, fits perfectly with nDOFs_=6
   - Benefit: memory efficient, automatic migration

5. Anti-symmetric A structure with 6 elements (Q17)
   - Could have: stored full 9 elements of 3×3 matrix
   - Optimization: exploit a_ij = -a_ji structure
   - Storage: [a_11, a_22, a_33, a_12, a_13, a_23] (6 elements)
   - Impact: 33% memory reduction for A_hist

6. f_hist only for velocity (Q17)
   - Initial: thought f_hist needed for all 6 DOFs
   - Insight: dx/dt = u has no forcing term (kinematic constraint)
   - Optimization: only store f for velocity (3 elements vs 6)
   - Impact: reduced from 12×solverOrder to 9×solverOrder properties

**Key Insights That Shaped Design**:
1. "dx/dt = u is physics-independent" (Q17 section 4)
   - This is a universal kinematic constraint, not physics-specific
   - Holds for ANY particle force model
   - Enables decoupling: position can be explicit

2. "Position history still useful despite explicit update"
   - BDF formula for position needs history: x^{n+1} = f(u^{n+1}, x^{n}, ...)
   - Potential use for extrapolation or diagnostics
   - Small cost: only 3×solverOrder additional properties

3. "nDOFs_=6 makes everything fit perfectly"
   - Discovered late: this resolves all memory sizing concerns
   - o_ydot sized for solverOrder×6×N perfectly holds A_hist (6 elem/level)
   - No new allocations needed, just reuse existing infrastructure

**Implementation Philosophy**:
- Reuse existing patterns (laggedInterpFields, properties, field registration)
- Minimize changes to migration/communication code
- Exploit physics structure for computational efficiency
- Document everything for future maintainers (this file!)

**What We Avoided**:
- ✗ Separate arrays requiring migration changes
- ✗ Full 6×6 solve (unnecessary 4× overhead)
- ✗ Storing redundant A matrix elements (33% waste)
- ✗ Storing f for position (50% waste for f_hist)
- ✗ Split nEXT vs solverOrder parameters (added complexity)

Q1: Why keep nEXT and solverOrder separate? Should we use solverOrder for both BDF and extrapolation?
--------------------------------------------------------------------------------
A: **Decision for LPM BDFEXT**: We will use `solverOrder` for BOTH purposes.

   Historical context (from fluid solver BDFEXT):
   - solverOrder: Controls BDF discretization of time derivative
   - nEXT: Controls extrapolation order for nonlinear terms
   - Kept separate for flexibility (e.g., BDF3 with 2nd-order extrapolation)
   
   **LPM BDFEXT simplification**:
   - solverOrder controls BOTH:
     * BDF discretization: Σ α_j * q^{n-j+1} / Δt (uses solverOrder history levels)
     * Extrapolation: A^{n+1} ≈ Σ β_j * A^{n-j+1}, f^{n+1} ≈ Σ β_j * f^{n-j+1}
   - Same order for both ensures consistency and simplicity
   - Storage: A_hist and f_hist need `solverOrder` levels (not nEXT)
   
   Rationale:
   1. Simpler implementation: one parameter controls everything
   2. Consistent accuracy: BDF-k with k-th order extrapolation is well-matched
   3. Memory sizing: o_ydot sized for `solverOrder` levels works perfectly
   
   Example: BDF3 (solverOrder=3) uses:
   - 3 past positions: q^{n}, q^{n-1}, q^{n-2}
   - 3 past A matrices: A^{n}, A^{n-1}, A^{n-2}  
   - 3 past forcing: f^{n}, f^{n-1}, f^{n-2}
   - All extrapolated with 3rd-order formula

Q2: What are A and f in the BDFEXT formulation? What DOFs does BDFEXT solve for?
--------------------------------------------------------------------------------
A: BDFEXT solves for both particle position AND velocity (6 DOFs total).

**State vector for BDFEXT**:
```
q = [x, y, z, u, v, w]^T  (6 components)
```
where:
- (x, y, z) = particle position
- (u, v, w) = particle velocity

This is different from AB/RK which only track position (3 DOFs) and compute velocity via dq/dt.

**Decoupled ODE structure**:
```
Position: dx/dt = u  (kinematic relationship)
Velocity: du/dt = A(t) * u + f(t)  (dynamics)
```

**KEY SIMPLIFICATION**:
- Position equation is trivial: dx/dt = u (no forcing, no A matrix)
- Only velocity equation needs implicit treatment
- This reduces the implicit solve from 6×6 to 3×3!

**Solution strategy**:
1. Solve velocity implicitly: (α_0/Δt - A^{n+1}) * u^{n+1} = RHS  (3×3 system)
2. Update position explicitly: x^{n+1} uses BDF of position history + newly computed u

**Why 6 DOFs?**
- BDFEXT needs particle velocity explicitly for physics evaluation
- Velocity dynamics include complex forces (drag, Coriolis, Basset history, etc.)
- Position is slave variable (kinematically determined from velocity)
- Allows more complex particle dynamics than simple trajectory tracking

Implications for memory:
- nDOFs_ = 6 for BDFEXT (vs 3 for AB/RK)
- o_y sized: 6 * fieldOffset_ (stores both position and velocity)
- o_ydot sized: solverOrder * 6 * fieldOffset_ (perfect fit for A_hist!)

In BDFEXT, these terms are treated differently:

**A term (implicit treatment)**:
- Moved to LHS: dq/dt - A*q = f
- Extrapolated from history: A^{n+1} ≈ Σ β_j * A^{n-j+1} (solverOrder levels)
- Combined with BDF discretization of dq/dt
- Results in implicit system: (BDF_coeff - A^{n+1}) * q^{n+1} = RHS

**f term (explicit treatment)**:
- Remains on RHS
- Also extrapolated from history: f^{n+1} ≈ Σ β_j * f^{n-j+1} (solverOrder levels)
- Contributes to RHS along with BDF history of q

Key insight: By moving A*q to LHS, we make the scheme more stable for stiff
systems where A might represent strong coupling (e.g., Coriolis, Basset history).

**Where do A and f come from?**:
- Physics-dependent: determined by particle force model
- Computed from interpolated fluid fields (velocity, vorticity, DuDt) + particle properties
- Examples:
  * Maxey-Riley: A from density ratio, added mass; f from pressure gradient, gravity
  * Rotating frame: A from Coriolis matrix; f from centrifugal, fluid drag
- User provides evaluation function (like userRHS for AB/RK)

**Structure of A**:
- For 6 DOF system (position + velocity), A is 6×6 matrix
- Often has block structure based on physics
- Anti-symmetric components (e.g., Coriolis) plus diagonal (e.g., drag)
- Full storage: 36 elements; structured storage: fewer (depends on physics)
- **Decision**: Store compact representation based on physics model structure

Storage needs (per particle, per time level):
- A_hist: Compact representation × solverOrder levels (size TBD based on physics)
- f_hist: 6 elements (force on 6 DOFs) × solverOrder levels
- Both extrapolated using same coefficients β_j from solverOrder

Note: With nDOFs_=6 for BDFEXT, memory allocations automatically sized correctly!
- Both extrapolated using same coefficients β_j from solverOrder

Q3: How is the implicit system solved? What size is the linear system?
--------------------------------------------------------------------------------
A: **KEY: Only velocity is solved implicitly - 3×3 system per particle!**

Due to the decoupled structure (see Q2):
- Position: dx/dt = u (explicit, no solve needed)
- Velocity: du/dt = A(t)*u + f(t) (implicit solve)

**Velocity system (3×3)**:
```
M * u^{n+1} = b
where M = (α_0/Δt) * I - A^{n+1}  (3×3 matrix)
      b = RHS from BDF history + extrapolated forcing
      u^{n+1} = [u, v, w]^T (velocity only)
```

**Properties of M**:
- α_0/Δt is a positive scalar (from BDF formula)
- A^{n+1} is 3×3, structure depends on physics (often anti-symmetric + diagonal)
- M is generally non-symmetric
- Dense 3×3

**Solution strategy (direct solve)**:
- 3×3 LU decomposition or analytical inversion
- ~30-50 FLOPs per particle
- Deterministic, no convergence concerns
- Highly parallelizable across particles

**Position update (explicit)**:
After solving for u^{n+1}, update position using BDF formula:
```
x^{n+1} = (1/α_0) * [Δt * u^{n+1} - Σ(j>0) α_j * x^{n-j+1}]
```
This is explicit - just weighted sum of history + new velocity.

**Two-stage algorithm**:
```
1. Extrapolate A and f from history
2. Solve velocity: M * u^{n+1} = b (3×3 implicit solve)
3. Update position: x^{n+1} = f(u^{n+1}, x_history) (explicit)
```

**Benefit**: Reduced from 6×6 (~200 FLOPs) to 3×3 (~50 FLOPs) - 4× speedup!

Implementation notes:
- Use direct 3×3 solver in kernel
- Can use Cramer's rule, LU, or other optimized 3×3 routines
- Check det(M) ≠ 0 for diagnostics
- Exploit A structure if possible (e.g., anti-symmetric)

Q4: How are A and f evaluated? User callback or built-in physics?
--------------------------------------------------------------------------------
A: **Current plan**: Built-in physics functions (user callback deferred to future).

Evolution of approach:
1. **Future vision**: User-provided callback (maximum flexibility)
   ```cpp
   using BDFEXTPhysics = std::function<void(lpm_t*, dfloat time,
                                             const deviceMemory<dfloat>& o_interpFlds,
                                             deviceMemory<dfloat>& o_A,
                                             deviceMemory<dfloat>& o_f)>;
   ```
   - User computes A and f from any interpolated fields
   - Can add custom dynamic fields via ensureBDFEXTInterpFields pattern
   - Analogous to userRHS_ for AB/RK solvers

2. **Current implementation**: Built-in physics models
   - Implement specific force models directly (e.g., Maxey-Riley, Stokes drag)
   - Hard-coded evaluation of A and f from known interpFields
   - Simpler to develop and test initially
   - Can refactor to callback pattern later

Evaluation timing:
- Called once per timestep (after interpolation, before integration)
- Computes A^{n} and f^{n} using current flow state
- Stored in A_hist[0] and f_hist[0] (index 0 = current time)
- Old history shifted: A_hist[i] ← A_hist[i-1] for i = solverOrder-1 down to 1

Workflow in integrate():
```
1. Interpolate fields to particle locations
2. Evaluate physics: A^{n}, f^{n} = evaluateBDFEXTPhysics(interpFields, properties)
3. Shift history: A_hist and f_hist
4. Extrapolate: A^{n+1}, f^{n+1} from history using EXT coefficients
5. Solve: (α_0/Δt - A^{n+1}) * q^{n+1} = RHS
6. Update: q^{n} ← q^{n+1}, shift y_hist
```

Future work:
- Add callback mechanism (like userRHS_) for custom physics
- Modify ensureBDFEXTInterpFields() to be user-callable for custom fields
- Provide example physics models as reference implementations

Q5: What coefficients are used for BDF discretization vs extrapolation?
--------------------------------------------------------------------------------
A: Different coefficient sets, both supporting variable timestepping.

**BDF coefficients (α)**: For discretizing time derivative
- Formula: Σ α_j * q^{n-j+1} / Δt ≈ dq/dt at t^{n+1}
- Depends on: solverOrder and timestep ratios Δt^{n}/Δt^{n-1}, etc.
- Constant timestep formulas (standard):
  * BDF1: α_0=1, α_1=-1
  * BDF2: α_0=3/2, α_1=-2, α_2=1/2
  * BDF3: α_0=11/6, α_1=-3, α_2=3/2, α_3=-1/3
- Variable timestep: More complex, depends on dt ratios (to be researched)
- See nek::coeffBDFEXT() in nekRS for reference implementation

**Extrapolation coefficients (β)**: For predicting A^{n+1}, f^{n+1}
- Formula: A^{n+1} ≈ Σ β_j * A^{n-j+1}
- Can follow laggedInterpFields pattern (already handles variable dt)
- Likely same as EXT coefficients used for fluid solver
- Check nek::coeffEXT() or similar

Key insight from laggedInterpFields:
- Coefficients computed in abCoeff(), extCoeff(), etc.
- Support variable dt via timestep history dt[]
- Can reuse this infrastructure for BDFEXT extrapolation

Implementation approach:
1. Create bdfCoeff() method (analogous to abCoeff())
   - Computes α coefficients from dt[] history
   - Stores in o_coeffBDF or similar
2. Reuse existing extCoeff() for β coefficients
   - Already supports variable dt
   - Used for laggedInterpFields extrapolation
3. Apply in kernel:
   ```
   A_ext = Σ β_j * A_hist[j]  // extrapolate to n+1
   f_ext = Σ β_j * f_hist[j]
   
   BDF_term = Σ α_j * y_hist[j] / dt  // for j > 0
   
   M = (α_0/dt) * I - A_ext
   b = f_ext + BDF_term
   
   q_new = M^{-1} * b
   ```

Research needed: Exact BDF coefficient formulas for variable timestep case.

Q6: Why do we need dynamic interpolation fields? Why not just register all fields statically?
--------------------------------------------------------------------------------
A: Some fields are *derived quantities* that must be recomputed each timestep:

   Static fields (o_U, o_P, o_S):
   - Already exist in device memory
   - Maintained by the fluid solver
   - Values persist across timesteps
   - Just need pointer to existing occa::memory
   
   Dynamic fields (vorticity, DuDt):
   - Don't exist as standalone arrays in nrs_t
   - Must be computed from primitive variables each step:
     * Vorticity: compute ∇×u from velocity gradients (strainRotationRate kernel)
     * DuDt: material derivative ∂u/∂t + (u·∇)u (from momentum equation assembly)
   
   - Values are *transient* - only valid for current timestep
   - Recomputing ensures consistency with current flow state
   
   The dynamic field mechanism:
   1. Register a "provider" lambda that knows how to compute the field
   2. Before interpolation, call all providers to get fresh data
   3. Use that data for point interpolation
   4. After interpolation, derived fields can be discarded (or providers cache them)
   
   This is more memory-efficient than forcing the fluid solver to maintain 
   permanent arrays for every possible derived quantity particles might need.

Q5: What's the difference between deviceMemory<T> and device.malloc()?
--------------------------------------------------------------------------------
A: They're equivalent ways to allocate device memory in OCCA:

   device.malloc():
   - Returns raw occa::memory (generic handle)
   - Example: device.malloc(nTotal * sizeof(dfloat))
   - Type-agnostic, requires manual sizeof() calculation
   
   deviceMemory<T>():
   - RAII wrapper around occa::memory
   - Returns deviceMemory<T> which IS-A occa::memory (implicit conversion)
   - Example: deviceMemory<dfloat>(nTotal)
   - Type-aware, handles sizeof automatically
   - Provides typed methods: resize(), slice(), copyFrom(), etc.
   
   Both use the same underlying ref-counted occa::memory handle, so:
   - No memory leaks when variables go out of scope
   - Can pass deviceMemory<T> where occa::memory is expected
   - Can store either in containers, return from functions safely
   
   Recommendation: Use deviceMemory<T> for clarity unless you need to match 
   existing code that uses device.malloc().

Q4: Why store lowercase names in dynamicInterpFields when the user might pass uppercase?
--------------------------------------------------------------------------------
A: Consistency with the rest of LPM's field registration system:

   interpFieldInputs map uses lowercase keys:
   - Internally calls lowerCase() before insertion
   - Lookup via interpFieldIds.count(lowerCase(name))
   
   If dynamicInterpFields stored original case:
   - field.name = "Vorticity"
   - interpFieldInputs["vorticity"] = ... (lowercase)
   - Mismatch when refreshing: would create new entry or fail lookup
   
   By normalizing at registration time:
   - addDynamicInterpField converts to lowercase immediately
   - Stores lowercase in both dynamicInterpFields AND interpFieldInputs
   - refreshDynamicInterpFields uses field.name (already lowercase) directly
   - No case-sensitivity bugs possible
   
   Trade-off: Lose original capitalization for error messages, but gain 
   robustness. Users should use lowercase consistently anyway.

Q5: Is the size check in refreshDynamicInterpFields() redundant?
--------------------------------------------------------------------------------
A: Yes, it's redundant with the check in addDynamicInterpField():

   Registration time (addDynamicInterpField):
   - Calls provider() to get initial data
   - Validates: data.size() == Nfields * fieldOffset
   - Only adds to dynamicInterpFields if validation passes
   
   Refresh time (refreshDynamicInterpFields):
   - Calls same provider() function
   - Provider *should* return same size every time
   - If size changes, it's a serious bug in the provider itself
   
   Keeping the check:
   + Defensive: catches provider bugs at runtime
   + Cost: negligible (one integer comparison per field per timestep)
   - Clutter: adds code that "shouldn't" be needed
   
   Removing the check:
   + Cleaner: trust that provider is well-behaved
   + Assumption: size validated once at registration is sufficient
   - Risk: silent corruption if provider has state-dependent size bug
   
   Recommendation: Keep it simple, remove redundant check. If provider is 
   broken, you'll get segfaults or device errors anyway (hard to miss).

Q6: Is .at() more expensive than operator[] for std::map?
--------------------------------------------------------------------------------
A: Negligibly more expensive, but worth it for safety:

   Performance (both are O(1) average):
   - operator[]: hash lookup + branch check + (insert default if missing)
   - .at():      hash lookup + branch check + (throw exception if missing)
   
   Difference: ~5-10 nanoseconds (exception construction overhead on failure path)
   
   In context of refreshDynamicInterpFields():
   - Provider call (kernel launch): ~1,000-10,000 nanoseconds
   - Map access overhead:          ~5-10 nanoseconds
   - Provider is 100-1000x more expensive than map access
   
   Safety advantage of .at():
   - operator[]: Silently creates entry with default value (occa::memory()) if missing
                 → Hard-to-debug null pointer bugs later
   - .at():      Throws exception immediately if key missing
                 → Fast feedback, easy to diagnose
   
   Conclusion: Use .at() in non-critical paths (once per timestep per field).
   Only use operator[] in hot loops (per-particle, per-element) or when you 
   explicitly want insert-if-missing behavior.

Q7: What is the micro-optimization with .at() vs operator[]?
--------------------------------------------------------------------------------
A: The performance difference comes from what happens when the key is missing:

   operator[] internals:
   ```cpp
   T& operator[](const Key& key) {
       iterator it = find(key);  // Hash lookup
       if (it == end()) {
           it = insert({key, T()}).first;  // Insert default value
       }
       return it->second;
   }
   ```
   
   .at() internals:
   ```cpp
   T& at(const Key& key) {
       iterator it = find(key);  // Same hash lookup
       if (it == end()) {
           throw std::out_of_range("key not found");  // Throw exception
       }
       return it->second;
   }
   ```
   
   When key EXISTS (normal case in refreshDynamicInterpFields):
   - Both: hash lookup (~10-50 ns) + branch check (1-2 CPU cycles)
   - Modern branch predictors handle "found" case near-perfectly
   - Difference: ~0-5 nanoseconds (noise level)
   
   When key MISSING (bug case):
   - operator[]: Inserts occa::memory() silently → deferred bug
   - .at():      Constructs exception (~100+ ns) → immediate crash
   
   Why it doesn't matter:
   - Your provider() calls cost 1,000-10,000+ nanoseconds (kernel launch)
   - Map access is 0.1-1% of total time
   - The "optimization" is unmeasurable in this context
   
   Recommendation: Micro-optimize when:
   - You're in a hot loop (millions of iterations)
   - Profiler shows map access as bottleneck
   - NOT when calling expensive operations like GPU kernels
   
   Use .at() for safety unless you have evidence it matters.

   Q8: How does the nekRS timer system work and how can I use it for performance profiling?
   --------------------------------------------------------------------------------
   A: nekRS has a centralized timer system accessed via `platform->timer`:

       Basic Interface (timer::timer_t):
       ```cpp
       // Start timing a region
       platform->timer.tic("myTag");
   
       // ... code to time ...
   
       // Stop timing
       platform->timer.toc("myTag");
   
       // Query results
       double elapsed = platform->timer.query("myTag", "DEVICE:MAX");
       long long int callCount = platform->timer.count("myTag");
       ```
   
       Key Methods:
       - tic(tag): Start timer for region identified by 'tag'
       - toc(tag): Stop timer and accumulate time
       - hostTic/hostToc: CPU-only timing
       - deviceTic/deviceToc: GPU-only timing (with device sync)
       - query(tag, metric): Get timing statistics
          * Metrics: "DEVICE:MAX", "HOST:MAX", "DEVICE:MIN", "HOST:MIN", etc.
       - count(tag): Number of times tic/toc was called
       - tags(): List all registered timer tags
   
       Hierarchical Naming Convention:
       nekRS uses "::" to create timer hierarchies:
       ```cpp
       platform->timer.tic("lpm_t::integrate");
       platform->timer.tic("lpm_t::integrate::find");
       platform->timer.tic("lpm_t::integrate::userRHS");
       platform->timer.tic("lpm_t::integrate::userRHS::interpolate");
       ```
   
       This creates a tree structure printed like:
       ```
       > lpm_t::integrate 0.125s
       >> lpm_t::integrate::find 0.030s
       >> lpm_t::integrate::userRHS 0.085s
       >>> lpm_t::integrate::userRHS::interpolate 0.070s
       ```
   
       LPM Pattern (with timer levels):
       LPM uses TimerLevel enum to control verbosity:
       ```cpp
       enum class TimerLevel { None, Basic, Detailed };
       ```
   
       Conditional timing example from lpm.cpp:
       ```cpp
       if (timerLevel != TimerLevel::None) {
             platform->timer.tic(timerName + "integrate");
       }
       // ... integration code ...
       if (timerLevel != TimerLevel::None) {
             platform->timer.toc(timerName + "integrate");
       }
       ```
   
       Member variables in lpm_t:
       - timerName: String prefix for all timers (default: "lpm_t::")
       - timerLevel: Controls which timers are active
          * None: No timing
          * Basic: Only major operations (integrate, find)
          * Detailed: All operations including sub-steps
   
       How to Use in BDFEXT Implementation:
   
       1. For refreshDynamicInterpFields():
       ```cpp
       void lpm_t::refreshDynamicInterpFields() {
          if (timerLevel == TimerLevel::Detailed) {
             platform->timer.tic(timerName + "integrate::refreshDynamic");
          }
     
          for (const auto &f : dynamicInterpFields) {
             interpFieldInputs.at(f.name) = f.provider();
          }
     
          if (timerLevel == TimerLevel::Detailed) {
             platform->timer.toc(timerName + "integrate::refreshDynamic");
          }
       }
       ```
   
       2. For individual provider profiling (very detailed):
       ```cpp
       if (timerLevel == TimerLevel::Detailed) {
          platform->timer.tic(timerName + "integrate::refreshDynamic::" + f.name);
       }
       interpFieldInputs.at(f.name) = f.provider();
       if (timerLevel == TimerLevel::Detailed) {
          platform->timer.toc(timerName + "integrate::refreshDynamic::" + f.name);
       }
       ```
   
       3. For BDFEXT integration kernel (later):
       ```cpp
       if (timerLevel != TimerLevel::None) {
          platform->timer.tic(timerName + "integrate::solveBDFEXT");
       }
       // ... 3x3 solve kernel ...
       if (timerLevel != TimerLevel::None) {
          platform->timer.toc(timerName + "integrate::solveBDFEXT");
       }
       ```
   
       Best Practices:
       - Use timerName prefix for all LPM-related timers (ensures filtering in printTimers())
       - Use "::" separator to create logical hierarchy
       - Guard with timerLevel checks to avoid overhead when timing disabled
       - Use TimerLevel::Detailed for fine-grained profiling (per-field, per-kernel)
       - Use TimerLevel::Basic for coarse-grained (integrate, find, migrate)
       - Call platform->timer.toc() even if early return/exception possible (or use RAII wrapper)
   
       Printing Results:
       ```cpp
       lpm->setTimerLevel(TimerLevel::Detailed);  // Enable detailed timing
       lpm->integrate(tf);
       lpm->printTimers();  // Prints hierarchical tree of all lpm_t:: timers
       ```
   
       Performance Overhead:
       - tic/toc with no sync: ~10-50 nanoseconds (hash map insert + clock read)
       - deviceTic/deviceToc with sync: ~microseconds (forces device synchronization!)
       - Conditional check (timerLevel != None): ~1-2 CPU cycles (branch prediction)
   
       Recommendation for BDFEXT:
       - Start with TimerLevel::Basic for major operations
       - Add Detailed timing for refreshDynamicInterpFields to measure provider cost
       - This will answer: "Is vorticity computation expensive? DuDt?"
       - Later: time BDFEXT solve kernel vs AB/RK integration

   Q10: Where should refreshDynamicInterpFields() be called and why?
   --------------------------------------------------------------------------------
   A: Call it in two places in the top-level timestep loop (integrate), not inside
       the RK/AB integrators:

       1) Early-exit path (time >= tf), before caching current values into
            laggedInterpFields:
            - Reason: When no step is taken, you still want dynamic fields (e.g.,
               vorticity, DuDt) to be computed once and stored as the most-recent
               level for later extrapolation and for restart consistency.

       2) End-of-step, right after setting time = tf and BEFORE shifting/copying
            into laggedInterpFields:
            - Reason: Ensure the stored t^n data for dynamic fields reflects the
               freshly computed values at the end of the step. Extrapolation for the
               next step uses these lagged histories.

       Not needed before interpolation:
       - The interpolation during userRHS uses extrapolatedInterpFields built from
          laggedInterpFields via extrapolateFluidState(). Since dynamic providers
          populate interpFieldInputs (the source for lagged updates), refreshing is
          only necessary before you copy into laggedInterpFields, not before
          interpolation itself.

       Timer placement:
       - Keep the refresh function tagged under
          `timerName + "integrate::refreshDynamic"` so it appears in the integrate
          timing hierarchy. Optionally add per-field sub-tags when profiling.

       Minimal code insertion points (for reference):
       - In integrate(), inside `if (time >= tf) { ... }` before the loop that copies
          from interpFieldInputs to laggedInterpFields.
       - In integrate(), after `time = tf;` and before the loop that shifts/copies
          into laggedInterpFields.

   Q11: Do we still need lagged histories of interpolated fields for BDFEXT?
   --------------------------------------------------------------------------------
   A: Not for the BDFEXT integrator math itself, provided you maintain per-particle
       histories of A and f (A_hist, f_hist) as designed.

       Distinctions:
       - laggedInterpFields: per-field histories of Eulerian fields interpolated to
          particles (used by AB/RK to build extrapolatedInterpFields for sub-steps).
       - A_hist, f_hist: per-particle histories of the linearized ODE coefficients
          used by BDFEXT to form A_ext and f_ext via extrapolation.

       BDFEXT path options:
       - Recommended: Compute current dynamic fields (e.g., vorticity, DuDt) → build
          current A and f → push into A_hist/f_hist → extrapolate A_ext/f_ext using
          coeffEXT. In this flow, laggedInterpFields are not required for the solver.

       When might laggedInterpFields still be useful?
       - Diagnostics/output: you may want time histories of velocity/vorticity at
          particle locations for post-processing.
       - Compatibility: parts of LPM (e.g., AB/RK, generic interpolation/extrapolate
          utilities) expect these containers; keeping them avoids conditional code.
       - Transitional phase: leave them on until BDFEXT is fully validated, then
          prune to save memory/time (nEXT*nFields*offset per field).

       Implementation guidance:
       - If solverType == BDFEXT, you can skip allocating/updating
          laggedInterpFields/extrapolatedInterpFields and rely solely on A_hist/f_hist.
       - Keep q_hist (velocity states) as properties for BDF recurrence; that is
          separate from laggedInterpFields.

   Q12: Why guard refreshDynamicInterpFields() with an empty check when the loop would just do nothing?
   --------------------------------------------------------------------------------
   A: It's optional; the empty check is a micro-optimization + intent signal, not a correctness requirement.

   Details:
   1. Function call overhead: Calling refreshDynamicInterpFields() when there are no dynamic fields still executes two branches (timerLevel check) and possibly tic/toc calls. Cost is tiny (~nanoseconds), so you can safely skip the emptiness guard unless integrate() is extremely hot.

   2. Timer pollution: If Detailed timing is on, calling tic/toc with zero work will still register the tag. With an emptiness check, "integrate::refreshDynamic" only appears when there is at least one dynamic field. (Subjective preference—some users like seeing zero-work regions, others don't.)

   3. Readability / intent: The if (!dynamicInterpFields.empty()) guard tells readers "this block only matters when dynamic providers exist". It can reduce cognitive load scanning integrate().

   4. Consistency: Other sections (e.g. lagging derivatives) guard on nParticles_ > 0. Following that style maintains uniform conditional patterns.

   5. Safety: Not needed—an empty vector for-each loop is well-defined and exits immediately. No functional difference.

   When to remove it:
    - You prefer simpler code and don't care about a timer appearing with zero work.
    - You later move provider calls into a different place and want fewer conditionals.

   When to keep it:
    - You want timer output to reflect real work only.
    - You may add assertions or logging inside refresh later and prefer not to trigger those without fields.

   Minimal alternative:
      // Unconditional call; loop just exits if empty
      refreshDynamicInterpFields();

Conclusion: Both styles are acceptable. Pick based on clarity preference; performance impact is negligible.

Q13: When should dynamic interpolation fields be refreshed in integrate()?
--------------------------------------------------------------------------------
A: Refresh at the START of integrate(), right after the early-exit check.

Timing and causality:
- When integrate(tf) is called:
  * Fluid solver has advanced to tf (= t^{n+1})
  * Particles are at `time` (= t^n)
  * Goal: advance particles from t^n → t^{n+1}

- Call refreshDynamicInterpFields() at the start to get current fluid data at t^{n+1}

Why BDFEXT needs current t^{n+1} data:
- BDFEXT is an IMPLICIT method:
  (α₀I - dt·A(t^{n+1}))·q^{n+1} = -Σ αⱼ·q^{n-j} + dt·f(t^{n+1})

- The implicit solve requires:
  * A(t^{n+1}) = Jacobian computed from current vorticity ω(t^{n+1})
  * f(t^{n+1}) = forcing from current DuDt(t^{n+1})

- This is inherently implicit coupling: particle state at t^{n+1} depends on 
  fluid state at t^{n+1}

Why AB/RK use laggedInterpFields instead:
- AB/RK are EXPLICIT methods with extrapolation for sub-steps
- They use laggedInterpFields (updated at end of previous step) for causality
- Current behavior: extrapolate from [t^n, t^{n-1}, ...] to predict intermediate states
- This is intentionally causal: particles use only "past" fluid data during their step

Implementation:
```cpp
void lpm_t::integrate(double tf) {
  // Early exit check...
  if (time >= tf) { ... }
  
  // Refresh dynamic fields to get current t^{n+1} fluid data
  refreshDynamicInterpFields();
  
  // BDFEXT: reads fresh interpFieldInputs directly to build A(t^{n+1}), f(t^{n+1})
  // AB/RK: use extrapolatedInterpFields from laggedInterpFields (causal)
  
  // ... run integrator ...
  
  // End: update laggedInterpFields for next step's AB/RK extrapolation
}
```

Key insight: Both coupling strategies coexist—BDFEXT uses current data (implicit), 
AB/RK use lagged data (explicit/causal).

Q14: How do lambda return types work in C++ and why does addDynamicInterpField need explicit return type?
--------------------------------------------------------------------------------
A: Lambdas in C++ can have their return type automatically deduced, but complex 
   types like occa::memory often need explicit specification.

Lambda syntax reminder:
```cpp
[capture](parameters) -> return_type { body }
```

Auto vs. explicit return type:
```cpp
// Auto deduction (works for simple types)
auto simple = [](int x) { return x + 1; };  // compiler deduces -> int

// Explicit return (needed for complex types)
auto complex = [this]() -> occa::memory {
  return nrs->strainRotationRate(false).slice(...);
};
```

Why addDynamicInterpField needs `-> occa::memory`:
- Parameter type is `std::function<occa::memory()>`
- Compiler must convert lambda to std::function
- For conversion, return type must be unambiguous
- `occa::memory` comes from method chaining (strainRotationRate().slice())
- Auto-deduction fails with complex expressions/method chains
- Solution: Explicitly write `-> occa::memory` after parameter list

Common error without explicit type:
```
no suitable user-defined conversion from "lambda []()-><error type>" 
to "std::function<occa::memory ()>" exists
```

Correct pattern for dynamic field providers:
```cpp
auto vorticityProvider = [this]() -> occa::memory {
  auto o_SijOij = nrs->strainRotationRate(false);
  return o_SijOij.slice(6*nrs->fieldOffset, 3*nrs->fieldOffset);
};

addDynamicInterpField("vorticity", 3, nrs->fieldOffset, vorticityProvider);
```

Key points:
- `[this]` captures the lpm_t instance so lambda can access nrs member
- `()` means no parameters (provider is called with no arguments)
- `-> occa::memory` explicitly tells compiler what the lambda returns
- Body calls nrs methods and returns occa::memory handle

Q16: How should position history be managed for BDFEXT? Should we follow the AB pattern?
--------------------------------------------------------------------------------
A: BDFEXT needs position history q^{n}, q^{n-1}, q^{n-2}, ... unlike AB which stores derivative history.

AB pattern analysis (for comparison):
```cpp
// In handleAllocation():
o_ydot = platform->device.malloc<dfloat>((solverOrder * nDOFs_) * offset);

// In integrateAB():
// Shift derivatives: ydot^{n-1} <- ydot^{n-2}, ydot^{n-2} <- ydot^{n-3}, ...
for (int s = solverOrder; s > 1; s--) {
  const auto N = nDOFs_ * fieldOffset_;
  o_ydot.copyFrom(o_ydot, N, (s - 1) * N, (s - 2) * N);
}
```

Memory layout: `o_ydot` stores [ydot^{n} | ydot^{n-1} | ... | ydot^{n-k+1}]
- Each level is `nDOFs_ * fieldOffset_` words
- Total size: `solverOrder * nDOFs_ * fieldOffset_`

BDFEXT needs similar pattern but for positions:

Option 1: Separate o_y_hist array (cleaner separation)
```cpp
// In handleAllocation() when solverType == BDFEXT:
o_y_hist = platform->device.malloc<dfloat>((solverOrder * nDOFs_) * offset);

// At end of integrate():
// Shift: y^{n-1} <- y^{n}, y^{n-2} <- y^{n-1}, ...
for (int s = solverOrder; s > 1; s--) {
  const auto N = nDOFs_ * fieldOffset_;
  o_y_hist.copyFrom(o_y_hist, N, (s - 1) * N, (s - 2) * N);
}
// Store current: y^{n} <- y^{n+1}
o_y_hist.copyFrom(o_y, nDOFs_ * fieldOffset_);
```

Option 2: Expand o_y to include history (matches AB style)
- Pro: Consistent with AB approach
- Con: o_y always refers to "current state" conceptually; mixing current + history is confusing
- Con: Complicates getDOF() and other accessors

Recommendation: Use Option 1 (separate o_y_hist)
- Clearer semantics: o_y is always "current state", o_y_hist is "past states"
- Only allocate when BDFEXT is used (saves memory for AB/RK)
- Easy to query: y^{n-j} is at offset `j * nDOFs_ * fieldOffset_`

Q17: How should BDFEXT history data (A, f, q) be stored? 
--------------------------------------------------------------------------------
A: BDFEXT needs to store A (coefficient matrix), f (forcing), and q (state) histories.
   Decision: Reuse existing arrays + particle properties to avoid migration changes.

Background (see Q2 for detailed formulation):
- Position: dx/dt = u (kinematic, no forcing needed)
- Velocity: du/dt = A(t)*u + f(t) (only velocity has A and f)
- A and f only apply to velocity equation (3×3 and 3-vector)
- Both A and f need history for extrapolation to t^{n+1}
- As per Q1 decision: both use `solverOrder` levels (not separate nEXT)

**KEY: nDOFs_ = 6 for BDFEXT** (position + velocity)
- This changes all memory calculations!
- o_y stores 6 components per particle: [x, y, z, u, v, w]
- o_ydot sized: solverOrder * 6 * fieldOffset_

BDFEXT storage requirements (all use solverOrder levels):
1. **A_hist**: 3×3 matrix for velocity equation × solverOrder × nParticles
2. **f_hist**: 3 elements (forcing on velocity only) × solverOrder × nParticles  
3. **q_hist**: 6 elements (state: pos+vel) × solverOrder × nParticles

Storage strategy (avoids modifying migration mechanism):

**1. Reuse o_ydot for A_hist**:
   - AB uses o_ydot to store derivative history
   - BDFEXT doesn't need derivatives (computed via BDF formula)
   - o_ydot sized: `solverOrder * nDOFs_ * fieldOffset_`
   - For BDFEXT with nDOFs_=6: `solverOrder * 6 * fieldOffset_`
   - **Perfect fit!** Can store A history with 6 elements per level
   
   **A matrix structure** (3×3 for velocity equation):
   - Full matrix: 9 elements
   - Often anti-symmetric + diagonal: 6 unique elements
   - Storage format: [a_11, a_22, a_33, a_12, a_13, a_23]
   - Reconstruct: a_ij = -a_ji for off-diagonal
   
   Memory layout in o_ydot (6 elements per A):
   ```
   [A^{n} (6) | A^{n-1} (6) | ... | A^{n-solverOrder+1} (6)]
   ```
   
   For BDF3 (solverOrder=3) with nDOFs_=6:
   - o_ydot size: 3 * 6 * N = 18N elements
   - A_hist needs: 3 * 6 * N = 18N elements ✓ Perfect fit!

**2. Store f_hist and q_hist as particle properties**:
   - Use addProperty() to register additional DOFs
   - f_hist: 3 × solverOrder components (velocity forcing only, e.g., 9 for BDF3)
   - q_hist: 6 × solverOrder components (position + velocity, e.g., 18 for BDF3)
   - Total: 9*solverOrder additional properties per particle (reduced from 12*solverOrder!)
   
   Property names:
   ```
   "f_hist_0_u", "f_hist_0_v", "f_hist_0_w",  // velocity forcing at t^{n}
   "f_hist_1_u", "f_hist_1_v", "f_hist_1_w",  // velocity forcing at t^{n-1}
   ...
   "q_hist_0_x", "q_hist_0_y", "q_hist_0_z",  // position at t^{n}
   "q_hist_0_u", "q_hist_0_v", "q_hist_0_w",  // velocity at t^{n}
   "q_hist_1_x", "q_hist_1_y", "q_hist_1_z",  // position at t^{n-1}
   "q_hist_1_u", "q_hist_1_v", "q_hist_1_w",  // velocity at t^{n-1}
   ...
   ```
   
   Note: No f_hist for position (dx/dt = u has no forcing term)
**3. Why this approach?**:
   - **No migration changes**: Properties automatically migrate with particles
   - **Memory efficient**: Reuses o_ydot instead of allocating new arrays
   - **Clean semantics**: o_ydot no longer used for derivatives in BDFEXT
   - **Consistent**: Properties already used for mass, temperature, etc.
   - **Simplified**: solverOrder used for all history (not nEXT vs solverOrder split)

**4. Design rationale - position vs velocity treatment**:
   
   **Universal physics constraint**:
   - dx/dt = u is ALWAYS true (kinematic relationship)
   - This holds for ANY particle physics model (Stokes, Maxey-Riley, etc.)
   - Position update is therefore always explicit/trivial after solving for u
   
   **Why save position history q_hist?**:
   - BDF formula for position requires history: x^{n+1} = f(u^{n+1}, x^{n}, x^{n-1}, ...)
   - Extrapolation of position may provide useful position estimate
   - Can be used for diagnostics, initial guesses, or adaptive timestepping
   - Minimal cost: only 3*solverOrder additional properties
   
   **Implicit vs explicit position update**:
   - Technically "semi-implicit": u^{n+1} solved implicitly, then x^{n+1} uses new u
   - From particle physics perspective: fully implicit (both updated together)
   - From linear algebra perspective: only velocity system needs matrix solve
   - Best of both worlds: implicit stability + explicit efficiency

Implementation notes:
- Register f_hist and q_hist properties in bdfextOrder() or initialize()
- Shift A history in o_ydot at end of integrate() (like AB shifts o_ydot)
- Shift f/q properties using kernel or host-side loops
- Access via getDOF("f_hist_j_u") or direct property indexing

Alternative considered (separate arrays):
- Pro: Clearer separation
- Con: Requires modifying migration, addParticles, deleteParticles
- Con: Extra memory allocation
- Rejected in favor of property-based approach

Q18: Property Naming and Registration Location
--------------------------------------------------------------------------------
**Question**: What is the final naming convention for history properties, and where exactly should they be registered?

**Context**:
We need to store `f_hist` (RHS history) and `q_hist` (state history) for BDFEXT.
We considered "bulk" properties (`f`, `y`) vs "per-component" (`f_hist_0_u`) vs "per-level" (`fhist0`).
We also debated registering in `bdfextOrder` vs `initialize`.

**Resolution**:
1.  **Naming Convention**: 1-based history indices.
    - `f1`, `f2`, ... `fk`: History of RHS ($f^n, f^{n-1}, \dots$).
    - `y1`, `y2`, ... `yk`: History of State ($y^n, y^{n-1}, \dots$).
    - `o_y` serves as `y0` (current state).
    - `f0` (current RHS) is treated as a transient local variable during integration and then shifted into `f1`.
    - Total `solverOrder` properties per variable type.

2.  **Registration Location**: `setupBDFEXT()` called from `initialize()`.
    - `bdfextOrder` is too early (mesh dimension might not be fully set, or nDOFs not finalized).
    - `initialize` is the right place because we know `solverType` and all dimensions.
    - `setupBDFEXT` (renamed from `ensureBDFEXTInterpFields`) handles all BDFEXT-specific setup:
        - Registers velocity DOFs (vx, vy, vz).
        - Registers interpolation fields (Velocity, Vorticity, DuDt).
        - Registers history properties (`fJ`, `yJ`).

3.  **Sizing**:
    - `fJ`: size `mesh->dim` (3).
    - `yJ`: size `nDOFs()` (6).

**Code Snippet**:
```cpp
void lpm_t::setupBDFEXT() {
  // ... register DOFs and fields ...
  // Index 1..k = history (f0 is transient)
  for (int j = 1; j <= solverOrder; ++j) {
    addProp(mesh->dim, "f" + std::to_string(j), false);
  }
  // Index 1..k = history (y0 is o_y)
  for (int j = 1; j <= solverOrder; ++j) {
    addProp(this->nDOFs(), "y" + std::to_string(j), false);
  }
}
```

Q19: Correction on Memory Strategy - Reusing o_ydot for State History
--------------------------------------------------------------------------------
**Question**: Q17 proposed using `o_ydot` for Matrix A history. Is there a better use for this memory?

**Analysis**:
- `o_ydot` is allocated as `solverOrder * nDOFs * fieldOffset`.
- In AB/RK, it stores derivatives ($dy/dt$).
- In BDFEXT, we don't explicitly store derivatives (they are implicit in the BDF formula).
- We DO need to store state history ($y^{n}, y^{n-1}, \dots$) for the BDF discretization.
- Storing state history in properties (as proposed in Q17/Q18) works but is slightly inefficient (extra map lookups, fragmented).

**New Decision**:
- **Reuse `o_ydot` to store State History ($y$)**.
- **Move Matrix A history to Properties**.

**Rationale**:
1.  **Size Match**: `o_ydot` is exactly the right size to store `solverOrder` levels of `y` (6 DOFs).
2.  **Semantics**: `o_ydot` is "history memory". Using it for `y` history is cleaner than using it for `A` matrices.
3.  **Aliasing**: We can create a reference `occa::memory& o_yHist = o_ydot;` in the code to make the intent clear.
4.  **Matrix A**: Since `o_ydot` is taken, `A` (6 components) moves to properties (`A1`, `A2`, ...). This is fine as `A` is just coefficients.

**Revised Storage Map**:
- `o_y`: Current state ($y^{n+1}$ being computed).
- `o_ydot` (alias `o_yHist`): History states $y^n, y^{n-1}, \dots$.
- Properties `f1`...`fk`: Forcing history (3 components).
- Properties `A1`...`fk`: Matrix A history (6 components).

Q20: Correct usage of copyFrom for history shifting
--------------------------------------------------------------------------------
**Question**: How do we correctly shift history arrays using `copyFrom`?

**Context**:
We need to shift history: $y^{n-k} \leftarrow y^{n-k+1}$.
This means copying *from* newer index *to* older index.

**API**:
`dest.copyFrom(src, count, destOffset, srcOffset)`

**Correct Pattern (Loop backwards)**:
To shift `o_yHist` (which stores $[y^n, y^{n-1}, \dots]$ at indices $0, 1, \dots$):
Actually, usually index 0 is most recent.
Let's say `o_yHist` stores $[y^n, y^{n-1}, y^{n-2}]$.
At step end, we want to push $y^{n+1}$ into slot 0, moving $y^n$ to slot 1, etc.

Shift loop:
```cpp
// Shift older levels: y[j] = y[j-1]
// Must go from oldest to newest to avoid overwriting
for (int j = solverOrder - 1; j > 0; --j) {
    size_t sz = nDOFs_ * fieldOffset_;
    // dest: j, src: j-1
    o_yHist.copyFrom(o_yHist, sz, j * sz, (j - 1) * sz);
}
// Capture current state into slot 0
o_yHist.copyFrom(o_y, nDOFs_ * fieldOffset_, 0, 0);
```

**Common Pitfall**:
Swapping `destOffset` and `srcOffset`.
Remember: `copyFrom(source, size, DEST_OFFSET, SRC_OFFSET)`.

Q21: Safe Property Access - propId() vs map[]
--------------------------------------------------------------------------------
**Question**: Why use `propId("name")` instead of `propIds["name"]`?

**Issue**:
`std::map::operator[]` ("`propIds["name"]`") has a side effect: if the key doesn't exist, it **inserts** a new entry with a default value (0) and returns it.
- If you typo a name, you get 0 instead of an error.
- If you access a property that hasn't been registered yet, you silently create garbage data.

**Solution**:
Use the helper function `propId("name")`.
- It handles case sensitivity (converts to lowercase).
- It checks for existence.
- It throws a clear error or returns a valid ID.
- It prevents accidental insertion of invalid keys.

**Code**:
```cpp
// BAD
int id = propIds["Velocity"]; // Might create "velocity" -> 0 if not found

// GOOD
int id = propId("Velocity"); // Throws if missing, handles case
```

o_ytmp = platform->device.malloc<dfloat>(nDOFs_ * offset);

3. **For velocity solve**:
   - Can overwrite portions after extrapolation is complete
   - No need for additional allocations

**Advantages**:
- No dynamic allocation overhead (eliminates poolDeviceMemory calls)
- Follows existing nekRS pattern (RK methods use o_k for stages)
- Memory already pinned and ready on device
- Consistent with how integrateRK() reuses o_k for k1, k2, k3, etc.

**Example Pattern** (from integrateRK2):
```cpp
occa::memory o_k1, o_k2;
{
  o_k1 = o_k + 0 * nDOFs_ * fieldOffset_;
  o_k2 = o_k + 1 * nDOFs_ * fieldOffset_;
}
```

**For BDFEXT**:
```cpp
auto o_fAext = o_k;                    // 7 components per particle
auto o_rhs = o_ytmp;                   // nDOFs_ per particle  
// ... perform computations ...
```

**Key Insight**: 
Pre-allocated buffers are a deliberate design pattern in nekRS to avoid 
malloc/free overhead during timestepping. Always check for existing buffers 
before introducing new allocations.

Q19: Available Matrix Solve Kernels in nekRS
================================================================================
**Date**: November 20, 2025
**Context**: Searching for existing linear solve functionality for 3×3 systems

**Question**: 
Does nekRS have a built-in kernel for solving Ax = b systems, especially for 
small 3×3 matrices?

**Answer**:
**NO general-purpose "solve Ax=b" kernel exists**, but there is relevant 
infrastructure:

**Found in src/core/elliptic/kernels/computeStiffnessMatrix.okl**:

1. **`determinant(double A[3][3])`** - Computes 3×3 determinant
   ```cpp
   double d_1 = A[0][0] * (A[1][1] * A[2][2] - A[2][1] * A[1][2]);
   double d_2 = A[0][1] * (A[1][0] * A[2][2] - A[2][0] * A[1][2]);
   double d_3 = A[0][2] * (A[1][0] * A[2][1] - A[2][0] * A[1][1]);
   return d_1 - d_2 + d_3;
   ```

2. **`inverse(double invA[3][3], double A[3][3])`** - Computes 3×3 matrix inverse
   - Uses cofactor method
   - Efficient for small matrices
   - **Device function** (not @kernel) - callable from within kernels

**Host-side** (not useful for kernels):
- `linAlg_t::matrixInverse(N, A)` in `src/platform/linAlg/matrixInverse.cpp`
- Uses LAPACK (dgetrf/dgetri) for general N×N
- CPU-only, not available on device

**Options for BDFEXT 3×3 Solve**:

**Option 1: Use existing inverse() + manual multiply**
```cpp
@kernel void solve3x3BDFEXT(...) {
  for (...) {
    // Build LHS matrix
    dfloat LHS[3][3];
    LHS[0][0] = g0 - dt*A_ext[0]; // diagonal
    LHS[1][1] = g0 - dt*A_ext[1];
    LHS[2][2] = g0 - dt*A_ext[2];
    LHS[0][1] = -dt*A_ext[3];     // off-diagonal
    // ... etc
    
    dfloat invLHS[3][3];
    inverse(invLHS, LHS);  // Call existing function
    
    // Matrix-vector multiply: v_new = invLHS * rhs
    for (int i = 0; i < 3; i++) {
      v_new[i] = invLHS[i][0]*rhs[0] + invLHS[i][1]*rhs[1] + invLHS[i][2]*rhs[2];
    }
  }
}
```

**Option 2: Implement Cramer's rule directly** (RECOMMENDED)
```cpp
@kernel void solve3x3BDFEXT(...) {
  for (...) {
    // Build LHS
    dfloat LHS[3][3] = { ... };
    
    // Compute determinant once
    dfloat det = determinant(LHS); // Use existing function
    
    // Solve using Cramer's rule (3 sub-determinants)
    v_new[0] = det_x / det;
    v_new[1] = det_y / det;
    v_new[2] = det_z / det;
  }
}
```

**Why Cramer's Rule is Better for 3×3**:
- More efficient: ~40 FLOPs vs ~60 for inverse + multiply
- Avoids computing full inverse (9 elements)
- Only need 4 determinants (1 main + 3 for numerators)
- Numerically stable for well-conditioned systems
- Direct solution without intermediate storage

**Implementation Note**:
The `inverse()` function is a **device function** (not @kernel), so it can be 
called from within your BDFEXT kernel but cannot be launched directly. This is 
the standard OCCA pattern for code reuse within kernels.

**Recommendation**:
Write a minimal custom kernel using Cramer's rule. You can reuse the existing 
`determinant()` function for the main determinant, then compute the three 
numerator determinants inline. Total kernel size: ~30-40 lines.

Q20: Kernel Implementation Strategy - Fused vs Decomposed
================================================================================
**Date**: November 20, 2025
**Context**: Deciding between monolithic kernel vs using built-in operations

**Question**: 
Should we write one large fused kernel that does everything (extrapolation, 
solve, update), or decompose the work using nekRS's built-in linAlg operations?

**Answer**:
**DECOMPOSED APPROACH RECOMMENDED** - matches nekRS design philosophy.

**nekRS Coding Principles** (from codebase analysis):
1. **Prefer core/built-in kernels when possible**
   - nStagesSumMany, linAlg operations (axpby, fill, etc.)
   - Well-tested, optimized, maintained
   
2. **Write custom kernels only for domain-specific operations**
   - Operations unique to your module
   - Can't be expressed with existing primitives
   
3. **Keep kernels focused and simple**
   - Single responsibility
   - Easier to debug, maintain, optimize
   
4. **Use @restrict for all kernel pointers**
   - Compiler hint for non-aliasing
   - Enables vectorization (10-50% speedup)

**Decomposed BDFEXT Implementation**:

**Step 1: Extrapolate properties** (BUILT-IN)
```cpp
// Use existing nStagesSumManyKernel
const auto Nprop = 7; // [f(3), A(4)]
auto o_fA = o_prop.slice(...);
auto o_fAext = o_k;
platform->linAlg->fill(Nprop*fieldOffset_, 0.0, o_fAext);
nStagesSumManyKernel(nParticles_, fieldOffset_, extOrder, Nprop, o_coeffEXTp, o_fA, o_fAext);
```

**Step 2: Build RHS** (BUILT-IN)
```cpp
// Use linAlg operations in loop
auto o_rhs = o_ytmp;
platform->linAlg->fill(nDOFs_*fieldOffset_, 0.0, o_rhs);

for (int i = 0; i < extOrder; i++) {
  auto o_yHist_i = o_yHist + i * nDOFs_ * fieldOffset_;
  platform->linAlg->axpbyMany(nParticles_, nDOFs_, fieldOffset_, 
                              coeffBDF[i], o_yHist_i, 1.0, o_rhs);
}

// Add dt*f_ext (velocity components only)
auto o_f_ext = o_fAext;
auto o_rhs_vel = o_rhs + velOffset;
platform->linAlg->axpbyMany(nParticles_, 3, fieldOffset_, 
                            dt, o_f_ext, 1.0, o_rhs_vel);
```

**Step 3: Solve 3×3 system** (CUSTOM KERNEL - minimal)
```cpp
// Only this needs custom kernel - ~30 lines
solve3x3BDFEXTKernel(nParticles_, fieldOffset_, g0, dt, 
                     o_A_ext, o_rhs_vel, o_v_new);
```

**Step 4: Update positions** (BUILT-IN)
```cpp
// Use linAlg->axpbyzMany
auto o_x_old = o_yHist + posOffset;
auto o_x_new = o_y + posOffset;
auto o_v_new = o_y + velOffset;
platform->linAlg->axpbyzMany(nParticles_, 3, fieldOffset_, 
                             1.0, o_x_old, dt, o_v_new, o_x_new);
```

**Step 5: Copy velocity** (BUILT-IN)
```cpp
// Use copyFrom or linAlg->copy
o_y.slice(velOffset, 3*fieldOffset_).copyFrom(o_v_new);
```

**Comparison**:

| Aspect | Fused Kernel | Decomposed |
|--------|-------------|------------|
| Lines of custom code | ~150 | ~30 |
| Kernel launches | 1 | ~6 |
| Maintainability | Complex | Simple |
| Debugging | Hard | Easy |
| Reusability | Low | High |
| Performance | Best | Excellent* |

*Kernel launch overhead is ~10-20 μs each, total ~100 μs for 6 launches.
For 10^5 particles, solve time >> launch overhead.

**Performance Analysis**:
- Kernel launch overhead: ~100-200 μs total (6 launches × 15-30 μs)
- Particle update time (10^5 particles): ~1-5 ms
- Launch overhead: < 5% of total time
- **Verdict**: Negligible performance cost for significantly better code quality

**The Custom Kernel** (only part needed):
```cpp
@kernel void solve3x3BDFEXT(const dlong nParticles,
                             const dlong fieldOffset,
                             const dfloat g0,
                             const dfloat dt,
                             @restrict const dfloat *A_ext,  // 4 components
                             @restrict const dfloat *rhs,    // 3 components
                             @restrict dfloat *v_new)        // 3 components
{
  for (dlong p = 0; p < nParticles; ++p; @tile(p_blockSize, @outer, @inner)) {
    // Build LHS = g0*I - dt*A
    dfloat LHS[3][3];
    LHS[0][0] = g0 - dt*A_ext[p + 0*fieldOffset]; // a_11
    LHS[1][1] = g0 - dt*A_ext[p + 1*fieldOffset]; // a_22
    LHS[2][2] = g0 - dt*A_ext[p + 2*fieldOffset]; // a_33
    
    const dfloat a12 = A_ext[p + 3*fieldOffset];
    LHS[0][1] = -dt*a12;
    LHS[1][0] =  dt*a12; // anti-symmetric
    
    // ... similar for a13, a23
    
    // Solve using Cramer's rule or call inverse()
    dfloat det = determinant(LHS);
    // ... compute v_new
  }
}
```
